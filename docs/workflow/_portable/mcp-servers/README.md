## 1. Why MCP servers are out of the generator

The 8 public-skill shims under `_portable/skills/` are description-triggered
**advisory** layers — they ship prompts, not capabilities. MCP servers are
the opposite: they expose **tools** the host can call (browser automation,
remote API access, etc.) and so live in the host tool's own MCP config, not
in the agent/skill registry.

Mixing them into `setup_subagents_v2.py --include-skills` would force the
generator to know about per-tool MCP config formats (Claude Code's
`.claude/mcp_servers.json`, Cursor's MCP settings, Codex CLI's MCP config)
and host-side install hooks. That breaks the generator's pure
`(Template) -> (Path, str)` contract. We keep MCP servers as a documentation
layer instead, so the user runs the install commands themselves.

## 2. Recommended MCP servers

The following MCP servers are reference-only recommendations — install them
based on your project's needs. The vendor cards (where applicable) live
alongside the public-skill bundle.

### 2.1 Playwright MCP (browser automation)

- **Why**: Enables description-triggered Playwright E2E for `feature-verify`
  workflows. Pair with the `superpowers` skill's plan-first discipline.
- **Upstream**: <https://github.com/microsoft/playwright-mcp>
- **License**: Apache-2.0.
- **Install (Claude Code)**:
  ```bash
  claude mcp add playwright npx '@playwright/mcp@latest'
  ```
- **Install (Cursor)**: add the same `npx @playwright/mcp@latest` invocation
  to Cursor's MCP settings. Cursor's settings UI accepts the same MCP
  Server-Sent-Events / stdio handshake.
- **Install (Codex CLI)**: not directly supported as of 2026-05 — track
  upstream Codex documentation for first-party MCP support.
- **First-run smoke test**: launch a browser session and `await
  page.goto('https://example.com')`. Verify the host tool reports the
  Playwright tools (`browser_launch`, `page_goto`, etc.).

### 2.2 Rube MCP (universal action layer)

- **Why**: 500+ pre-built tool integrations (Slack, GitHub, etc.) the host
  can call without bespoke tool wrappers.
- **Upstream**: <https://github.com/rube/mcp-server> (placeholder URL —
  update once the public repo is finalized in your fork).
- **License**: confirm with upstream before adoption; vendor card MUST land
  before the install command is run.
- **Install (Claude Code)**:
  ```bash
  claude mcp add rube <upstream-command>
  ```
- **Install (Cursor / Codex)**: same handshake, per host's MCP settings.

## 3. Maintaining the install README

When a project decides to add a new MCP server:

1. Land a vendor card under `docs/vendor-cards/<name>.md` first (license +
   sync owner + upstream commit pin) — same template the public-skill
   bundle uses.
2. Append a `### 2.x <Name> MCP` section above with the **command**,
   **license**, **first-run smoke test**.
3. Land the change in a commit that touches only `_portable/mcp-servers/`
   and the vendor card; do NOT modify the generation script.

`<skill_prefix>workflow-migrate resync` overwrites `<mcp_servers_root>` verbatim from
the source repo, so any project-customized notes belong in
`<project_workflow_doc>` (project-layer), not here.

## 4. What this is NOT

- Not an exhaustive MCP catalog — these are the two servers the source
  project recommends out of the box.
- Not a runtime config — the install commands above modify per-host
  settings, not portable-layer files.
- Not generated by `setup_subagents_v2.py --include-skills` — that script
  emits skill wrappers only. MCP install is hand-driven.
