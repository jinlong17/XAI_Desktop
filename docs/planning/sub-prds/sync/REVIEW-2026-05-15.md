## 总评

加密层方向对(KEK/DEK 分离、AES-256-GCM、Argon2id、零知识承诺),但**协议层离可实施成熟度还差一轮硬化**。如果按当前 PRD 直接进 Phase 0 子阶段 0.3,最可能出事的位置按概率从高到低:

1. **AES-GCM envelope 未绑定 AAD + 缺 replay/rollback 防护**:恶意或被攻破的 service_role 持有者可以静默调包/回滚密文,GCM tag 仍校验通过,客户端把新数据覆盖成旧状态,且**用户和客户端都察觉不到**——这是端到端加密产品最常见的"零知识幻觉"。
2. **12 词助记词编码 32B DEK 的实现层错误**:BIP-39 12 词只承载 128-bit 熵 + 4-bit checksum = 16.5 字节,不能无损编码 256-bit DEK。任何按字面实现的人都会在 `BIP39_encode(DEK)` 这一步引入数据损坏或截断,且这种错误在单元测试通过的情况下也会发生(测试者会在两端用同一份代码,看不出问题),最终用户走"助记词恢复"会拿到不可解密的旧 blob。
3. **LWW + tombstone 在客户端时钟/网络分区下的边界 case**:`updated_at` 与 `server_updated_at` 在 PRD 里混用、cursor 仅基于 timestamp、tombstone 永久优先、outbox 合并去重不顾依赖,这四个加起来让"最终一致"实际上是"最后一个写的盖掉所有人",并且**没有 loser shadow** —— 用户编辑被静默丢失没有任何痕迹。
4. **dev-plan §4.2 Tauri command 暴露 raw key 进 JS** 与 PRD §3.1.3 "Plugin 不能访问 DEK" 直接冲突。renderer XSS 或恶意 plugin 调一次 `crypto_decrypt(envelope, key)` 即可拿到所有内容。

零知识承诺本身的设计意图正确,但**当前协议无法对"恶意服务端"提供有意义的完整性/新鲜性保护**。这是首要修正方向。

## 安全性问题(按 CVSS v3.1 估算严重度)

> 行号引用 `PRD.md` v0.1-DRAFT,除非显式标注 `dev-plan`。
> CVSS 估算遵循 "在零知识假设破裂或攻击者已获 service_role 的情况下评估上限"。

### 🔴 Critical(可能导致数据泄漏 / 数据丢失 / 账号被盗)

#### C-01 主密码字符串原文进 Supabase Auth 端点(认证密码与 KEK 源未真正分离)
- 位置:§3.3 line 128-143、line 157 注释
- CVSS 9.6(AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H)
- 现状:`POST /auth/signup` body 携带 `password_hash_for_supabase` 与 `kek_salt`、`encrypted_dek`。第 157 行注释说"Supabase 见的密码哈希只能用来 login,不能解 KEK"。**这是不成立的**:Supabase Auth 接收的是客户端可控的字符串(无论叫不叫 hash),恶意/被攻破的 Supabase 在 signup/login 时拥有完整的 master_password 原文(因为客户端要让 Supabase 完成"密码校验",必然要把派生自同一 secret 的可验证材料发过去),配合 `kek_salt` 在数据库中就能离线跑 Argon2id 还原 KEK,解出 DEK。
- 攻击场景:Supabase 内部人员或拿到 service_role 的攻击者,从 `auth.users.encrypted_password`(bcrypt)对常用密码做字典攻击得到原文 master_password → 用 `accounts.kek_salt` 跑 Argon2id → 得 KEK → 解 `encrypted_dek` → 解所有 `encrypted_blobs.blob`。整个过程**不需要拖客户端**。
- 修正(择一):
  - (a) 改用 **OPAQUE**(RFC 9807 / draft-irtf-cfrg-opaque)做零知识口令认证,服务端永远拿不到口令材料,且 attacker 即使拿数据库 dump 也无法离线字典攻击。
  - (b) 退一步:让客户端用**与 KEK 完全不同的派生路径**生成 `auth_password`,例如 `auth_password = HKDF(master_password, salt=fixed_auth_salt, info="xai.auth.v1")`,然后用 OPRF / SRP 包一层,确保 Supabase 不接触到 master_password 原文。简化版至少应做:`auth_password = Argon2id(master_password, salt=email||"auth", t=1, m=16MiB)` —— 弱化的派生减小攻击面,但**仍不彻底**,长期还是应走 (a)。
  - (c) 在威胁模型 §2 显式声明 "T1 服务端被攻破" 不再"零知识",改为 "T1 攻破后,可对所有账号离线 Argon2id 字典攻击,弱口令账号在小时级被破解"。

#### C-02 AES-GCM envelope 未绑定 Associated Data(AAD)
- 位置:§5.2 FR-SY-07/08 line 274-276、§7.1 envelope 格式 line 558-568
- CVSS 9.1(AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H)
- 现状:envelope 二进制只含 `v|kdf|nonce|ciphertext|tag`,没有 AAD。这意味着**密文与其语境完全解耦**:同一 DEK 加密的任意 ciphertext 都可以被替换到任意 `(account_id, entity_type, entity_id)` 位置,GCM tag 仍验证通过。
- 攻击场景:
  1. 持有 service_role 的攻击者 SELECT 一条用户 A 的 `note` blob (entity_id=X),UPDATE 进 `todos` 表的 entity_id=Y 行。客户端 pull 后,把这条"实际是 note 内容"的 blob 当作 todo 解出来,UI 解析失败或显示成乱码——但**密码学层没有报错**,审计层只会看到一条"正常的 todo 更新"。
  2. 更恶毒的版本:把 `todos` 表中已删除(deleted_at != NULL)的 tombstone blob,替换到一条新 row 上,把 `deleted_at` 字段抹掉。客户端看到的是"一条复活的旧 todo",且 GCM 验证通过。
  3. 跨账号:同一 Supabase 项目内,不同账号 DEK 不同,所以跨账号失败 —— 但**同账号内跨实体可任意调包**。
- 修正:
  - envelope 增加 AAD 字段(或在加密时把 AAD 喂进去,只验证不存):`AAD = account_id || entity_type || entity_id || blob_version || key_id || (deleted_at flag) || schema_version`。
  - Rust 侧 `aes-gcm` crate 的 `encrypt_in_place_detached(nonce, aad, plaintext)`,decrypt 时同样传入 AAD。
  - 参考:[RFC 5116 §2.1 Authenticated Encryption Interface](https://www.rfc-editor.org/rfc/rfc5116#section-2.1) 强调 AEAD 的 associated data 是"必须由协议层绑定"的安全前提。

#### C-03 缺 replay / rollback 防护(可静默把客户端打回旧状态)
- 位置:§7.3-7.4 line 589-656、§6.1 `encrypted_blobs` 表结构 line 423-435
- CVSS 9.1(AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H)
- 现状:`version` 字段是客户端单调递增,服务端不校验、不存历史、不防回滚;客户端 pull 时按 `server_updated_at` 比较,没有 hash chain 或 Merkle root。
- 攻击场景:
  1. 服务端被攻破后,UPDATE 一条 30 天前的合法 ciphertext 进 `encrypted_blobs`,把 `server_updated_at = now()`。所有客户端下次 pull 时把这条旧 ciphertext 当成"最新版"应用,**把用户的最新版本覆盖成 30 天前的状态**。GCM tag 通过,AAD 通过(如果只绑定到 entity_id),用户无感知。
  2. 选择性回滚:攻击者只回滚某条"令攻击者尴尬"的 note,或回滚 todo "取消订阅 XX 服务"。
- 修正:
  - 每实体维护单调 `revision` 在加密 AAD 中(配合 C-02),客户端拒收 `revision < max_seen`。
  - 账号级 Merkle root / hash chain,客户端定期校验 root 一致性(参考 Signal Sealed Sender / Keybase Sigchain 的 STR — Signed Tree Root)。
  - 至少:客户端本地表 `entity_state(entity_id, max_seen_revision)`,pull 时强校验 `incoming.revision > local.max_seen`,否则拒收并 surface "服务器试图覆盖旧版本" 告警。
  - 若不做以上,**必须在威胁模型 §2 显式列入"T1.1 恶意服务端可静默回滚密文,零知识不防护"** —— 让用户知道残余风险。

#### C-04 助记词恢复 / 密码重置只验 bearer,服务端无法验证恢复者持有 DEK
- 位置:§3.5 line 175-182、§3.6 line 183-198、§7.2 `PATCH /auth/me` line 578
- CVSS 9.0(AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H)
- 现状:`PATCH /auth/me { kek_salt', encrypted_dek', kek_kdf_version=1 }` 只需 bearer token。
- 攻击场景:
  1. 攻击者通过钓鱼/Apple ID 接管邮箱 → 触发 Supabase 邮件重置 → 拿到新 bearer。
  2. PATCH 一个攻击者自己生成的 `encrypted_dek`(用攻击者知道的 KEK 加密任意 DEK)。**用户的历史 `encrypted_blobs` 立刻变成"用旧 DEK 加密,但 `encrypted_dek` 已被换成新 DEK"** —— 永久不可解密。
  3. 即使用户保存了助记词,助记词解出的是**旧 DEK**,但客户端登录后会拉到攻击者写入的新 encrypted_dek,导致需要回滚 + 用户教育流程,且窗口期内用户的数据丢失。
- 修正:
  - 恢复 / re-key 必须附 **recovery proof**:客户端用 (恢复路径推出的) DEK 派生 `auth_secret_recovery = HMAC(DEK, "xai.recovery.proof.v1")`,然后用 `auth_secret_recovery` 对 server challenge 做 MAC。服务端把 `expected_recovery_secret_hash` 在注册时存好,验证后才允许 PATCH `encrypted_dek`。
  - 注意:这个 hash 不能让 server 拿去离线字典攻击恢复 secret,所以应是 KDF 派生而非直接 hash。

#### C-05 12 词助记词编码 256-bit DEK 不成立(BIP-39 容量错配)
- 位置:§3.1 line 102、§3.3 line 134、§3.6 line 187-188
- CVSS 8.8(AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:H)
- 现状:`mnemonic = BIP39_encode(DEK)` 把 32 字节 DEK 编码成 12 词。[BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) 规范:`ENT/32 + ENT = MS * 11`,12 词只承载 128-bit 熵 + 4-bit checksum,**物理上无法编码 256-bit**。
- 后果:实现者必有以下三种错误之一,且都会让"助记词恢复"在实际场景下失败:
  - (a) 直接截断 DEK 前 16 字节编码 → 恢复出来的是只有 128-bit 熵的"DEK",再也解不开原 blob。
  - (b) 改用 24 词但代码没改,运行时报错。
  - (c) "12 词 + 派生"语义没定义,不同开发者实现成不同算法,跨版本恢复失败。
- 修正(必选):
  - (a) **24 词(256-bit 熵 + 8-bit checksum)直接编码 DEK** —— 这是 Bitcoin 生态最标准做法,有大量审计过的库(`@scure/bip39`、`bip39` Rust crate)。
  - (b) 12 词作为 **recovery seed**(128-bit 熵),通过 HKDF 派生 256-bit wrapping key,该 wrapping key 加密真正的 DEK 存到服务端的 `encrypted_dek_recovery` 字段。
  - 选 (a) 还是 (b) 是产品决策(24 词更长 UX 差,12 词需要额外字段),但**必须二选一,不能保持现状**。

#### C-06 Tauri command 暴露 raw key,违反 PRD §3.1.3 的不变式
- 位置:dev-plan §4.2 line 237-242
- CVSS 9.0(AV:L/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H)
- 现状:
  ```rust
  #[tauri::command] async fn crypto_encrypt(plaintext: Vec<u8>, key: Vec<u8>) -> Result<Vec<u8>, String>;
  #[tauri::command] async fn crypto_decrypt(envelope: Vec<u8>, key: Vec<u8>) -> Result<Vec<u8>, String>;
  ```
  JS 侧持有 raw key 才能调用这两个命令。这与 PRD §3.1 line 108 "Plugin 不能直接访问 DEK,必须通过 `core-data` 暴露的 `encrypt(record) / decrypt(blob)` 服务接口" 直接冲突。
- 攻击场景:
  1. 任何 renderer XSS(比如 markdown note 渲染、剪贴板内容渲染、Web Console 第三方依赖 supply chain)在 JS 进程拿到 DEK,Tauri IPC 没有 allowlist 校验 caller plugin 身份,可直接 `invoke('crypto_decrypt', { envelope: any_blob, key: stolen_dek })`。
  2. 恶意 plugin 即使在 PRD §5.10.1 plugin 沙箱里运行,只要能 invoke Tauri command 就能拿 key。
- 修正:
  - **DEK 常驻 Rust 侧 KeyVault**,JS 只拿 opaque `key_handle: KeyHandleId`。
  - 命令改成 `crypto_encrypt_for(entity_type, entity_id, plaintext) -> envelope`,Rust 侧自己查 KeyVault + 自己组装 AAD。
  - Tauri capability config 限制 `crypto_*` 命令只能被 `plugin-account` / `core-data` 调用,拒绝其他 plugin 和 renderer 直调。
  - JS 侧 `core-data.encrypt(record)` 必须经过 plugin 身份白名单中转。
- 这是**架构问题**,不是单点 bug,在 Phase 0 子阶段 0.3 实装前必须改图纸。

#### C-07 Re-key 流程缺 keyring,中断必导致部分数据永久不可读
- 位置:FR-SY-13 line 280、R-10.6 line 771、§7.1 envelope 缺 `key_id` line 558-568
- CVSS 8.7(AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:H)
- 现状:envelope 没有 `key_id`,`encrypted_blobs` 表没有 `key_generation` 字段;Re-key "两阶段" 是 R-10.6 提了一句但没有 schema 支撑。
- 攻击场景(=数据丢失场景):
  1. 用户触发 Re-key,客户端开始用 DEK_v2 重加密所有 blob 上传 staging。
  2. 上传到 70% 时进程崩溃 / 用户关机。
  3. 重启后 `account.encrypted_dek` 是 v1 还是 v2 都有问题:
     - 若已 swap 到 v2:30% 用 v1 加密的 blob 用 DEK_v2 解密失败,GCM tag fail,标 corrupt —— 用户数据丢 30%。
     - 若未 swap:70% staging blob 是 v2 加密的"孤儿",但 PRD 没说怎么 GC,且 staging blob 表都没设计。
- 修正:
  - envelope 增加 `key_id: u32`(配合 C-02 写入 AAD 防替换)。
  - `accounts` 增加 `current_dek_key_id`、`previous_dek_key_id`,加 `keyring` 关联表存所有曾用 DEK 的 `(key_id, encrypted_dek_by_kek)`。
  - Re-key 期间客户端**同时读 v1+v2**(按 blob 的 key_id),只在"全部 blob 已重加密 + 服务端 commit" 后才 retire v1。
  - Staging 设计写进 §6.1 表 schema,而不是放 R-10.6 一句话带过。

#### C-08 AES-GCM 不是 key-committing(Invisible Salamanders 攻击)
- 位置:§5.2 FR-SY-07/08、整个加密层
- CVSS 7.4(AV:N/AC:H/PR:H/UI:N/S:U/C:H/I:H/A:N) — 在多密钥 / re-key 场景下升级到 8.x
- 现状:AES-GCM 标准模式**不保证 key commitment**。攻击者可以构造一对 `(ciphertext, tag)`,使得它在两个不同的 DEK 下都能解密成功 —— 但解出两个不同的明文。[Invisible Salamanders, USENIX 2021](https://eprint.iacr.org/2019/016) 详细分析。
- 在 XAI_Desktop 场景下的攻击:
  1. Re-key 期间,客户端按 envelope `key_id` 选择 DEK 解密。攻击者(持 service_role)构造一个 ciphertext 让客户端在 `key_id=1` 下解出"todo: 买菜"、在 `key_id=2` 下解出"todo: 投毒"。
  2. 配合 C-03 的回滚攻击,攻击者可以在用户切换 DEK 时**让同一条 blob 在用户视角下"内容变了但没有显示更新时间变化"**。
- 修正:
  - 用 **AES-GCM-SIV**([RFC 8452](https://www.rfc-editor.org/rfc/rfc8452))或 **XChaCha20-Poly1305-Commitment**(libsodium `crypto_secretstream`)替代 AES-GCM。AES-GCM-SIV 是 key-committing 的弱形式;若要严格,用 [HtE / UtC 组合](https://eprint.iacr.org/2022/268)。
  - 退一步:在 plaintext 头部加入 32 字节 `commitment = HMAC(DEK, "commit"||AAD)`,解密后校验。
  - 若不修,**至少在 PRD §11 R-10 子风险新增 R-10.9 "Invisible Salamanders 风险,Re-key 期间不防护"**。

#### C-09 本地 SQLite 未定义加密策略(已解锁设备的冷数据完全裸奔)
- 位置:PRD 通篇未提、`core-data` 数据层未规范
- CVSS 7.8(AV:P/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N)
- 现状:PRD 多处提到 "本地 SQLite 缓存"(§3.1 line 108、§4.1 line 240、§5.6 line 319 等),但**没有任何地方说 SQLite 文件本身是否加密**。FR-AC-08 / FR-SY-10 只规定 KEK/DEK 不写盘;但**解密后的 plaintext rows 必然要写 SQLite 才能本地查询**(§4.1 line 240"服务端不索引...所有 entity 内部字段查询都在客户端 SQLite 上做")。
- 攻击场景:
  1. T3 "本机被盗(未解锁)" 之外有一个 PRD 没列的攻击者 **T3.5 "拿到 disk image"**(从 Time Machine、未加密的外接硬盘备份、坏掉送修的 Mac、家庭共享用户)。FileVault 是用户责任,默认不开。
  2. 攻击者直接 `sqlite3 ~/Library/Application Support/.../xai.db` 读所有 todos / notes / clipboard / habit_logs。零知识承诺**完全失效**(因为它只保护"在路上"和"在云端",不保护"在本机")。
- 修正(择一):
  - (a) **SQLCipher**:SQLite 文件级加密,key 由 KEK 派生(`db_key = HKDF(KEK, "xai.sqlite.v1")`),只在解锁状态下 attach。
  - (b) **字段级加密**:只把可查询字段(updated_at / entity_id / tags)留明文,其他敏感字段在 SQLite 里也存 ciphertext,运行时按需解密。性能 trade-off 大。
  - (c) **PRD 显式声明**:"本地 SQLite 不加密,依赖用户启用 FileVault",并在 onboarding 强制提示。这是 1Password 默认走的路。
  - 任选一种但**必须显式选择并写进 §2 威胁模型 + §10 验收**。

#### C-10 数据导出 JSON 无加密,FR-SY-50 把所有 E2E 数据明文落盘
- 位置:FR-SY-50 line 357、FR-AC-13 line 267
- CVSS 7.5(AV:L/AC:L/PR:H/UI:R/S:U/C:H/I:N/A:N)
- 现状:`xai-export-<date>.json` 是已解密的全量数据 JSON。
- 攻击场景:
  1. 用户为了"换工具" 导出 → 默认下载到 `~/Downloads/`。
  2. iCloud Drive / Dropbox / Google Drive 客户端把 `~/Downloads/` 整个同步上去(很多用户开了)。
  3. **所有原本受 E2E 保护的数据,现在以明文形式存在第三方云端**,与零知识承诺彻底冲突。
- 修正:

#### H-01 96-bit 随机 nonce 无 key/device 命名空间,长生命周期下生日界
- 位置:§5.2 FR-SY-07 line 274、§7.1 line 558-568
- CVSS 7.5(AV:N/AC:H/PR:H/UI:N/S:U/C:H/I:H/A:N)
- 现状:`12B 随机 nonce, 来自 OsRng`,1M 单测无碰撞。但 96-bit 随机 nonce 的 birthday bound 是 ~2^48 个消息;若一个重度用户的 DEK 长期不换、一天上万条 mutation × 多设备,几年内碰撞概率开始不可忽略。NIST SP 800-38D §8.3 明确"对随机 IV,推荐单 key 上限 2^32 messages"。
- 修正:
  - 推荐:用 **deterministic nonce** = `device_id (4B) || counter (8B)`,或 `key_id (4B) || counter (8B)`,counter 用客户端持久化的单调递增整数;碰撞概率为 0。
  - 替代:迁 AES-GCM-SIV(对 nonce-misuse resistant)或 XChaCha20-Poly1305(192-bit nonce 完全消除生日界顾虑)。
  - 至少在 FR-SY-07 写入"单 DEK 生命周期内 message 上限 2^32,达到需触发 Re-key"。

#### H-02 LWW 规则混用 `updated_at` / `server_updated_at` / device tie-break,规格不一致
- 位置:§5.4 FR-SY-22 line 299-300、FR-SY-23 line 300、FR-SY-24 line 301
- CVSS 7.8(协议一致性问题,CVSS 主要描述完整性)
- 现状:
  - FR-SY-22 说"取 updated_at 大者,equality 时取 device_id 字典序大者"。
  - FR-SY-23 说"server 用 server 时间盖戳 server_updated_at;client updated_at 仅作 tiebreak hint"。
  - 两个规则的字段不一致。如果是 `server_updated_at` 主排序,那 device_id tie-break 应该是"server_updated_at 相等时";如果是 `updated_at` 主排序,那"server 权威钟" 又是干嘛的?
- 修正:
  - 唯一权威排序应为 **`(server_commit_seq, account_id, entity_type, entity_id)`** 复合键。`server_commit_seq` 用 Postgres `BIGSERIAL` 在每次 commit 自增,**单调、唯一、可作 cursor**,根本不需要 timestamp 排序。

#### H-03 Tombstone 永远胜过 update,离线旧 delete 可覆盖在线新 edit
- 位置:FR-SY-24 line 301-302
- CVSS 8.1
- 现状:`tombstone 优先(deleted_at != NULL 永远胜过 updated_at)。例外:用户在 30 天内"撤销删除"触发 undelete 写新版本,该新版本 updated_at 必须 > 原 tombstone updated_at`。问题:**离线 7 天的设备 A 上有 delete(timestamp t0=7 天前),在线设备 B 在 t1=昨天编辑了这条**。设备 A 联网后 push delete → 服务端按"tombstone 优先" 接受 → 设备 B 下次 pull 时数据被覆盖删掉。"undelete"机制依赖 `updated_at > tombstone updated_at`,但 B 的 t1 确实 > t0 啊?那为什么 PRD 说 tombstone 优先?
- 修正:
  - **delete 也是 mutation**,按 commit_seq 排序决胜,**不要给 tombstone 特殊优先级**。
  - 真正需要"硬删" 是 "用户在 settings 点了清理" 这种语义,应在 PRD 区分 `soft_delete` vs `hard_delete`。
  - undelete 是新 revision,按统一规则决胜,不靠客户端时间比较。

#### H-04 PULL cursor 仅用 timestamp,同 ms 内多条 row 会丢
- 位置:§7.4 line 654 `next_cursor: "2026-05-15T10:00:00.100Z"`、§5.3 FR-SY-16 line 288
- CVSS 8.2
- 现状:`?since=<cursor>&limit=500`,cursor 是 ISO timestamp。当 500 条的最后一条与第 501 条 `server_updated_at` 相同(高频用户 + Postgres `now()` 在同毫秒内多次 commit 是常见的),下一次 pull `?since=<last_ts>` 用 `>` 会跳过 501-N 条同 ts 数据,用 `>=` 会无限循环。
- 修正:
  - 复合 cursor:`(server_updated_at, account_id, entity_type, entity_id)`,client 用 `WHERE (server_updated_at, entity_id) > (last_ts, last_eid)`。
  - 推荐:全局 `commit_seq BIGSERIAL` 严格单调,cursor 就是 `last_seen_seq`,简单且无歧义(对齐 H-02 修正)。

#### H-05 PUSH "永远接收 408 不发生" 静默覆盖冲突,无 loser shadow
- 位置:§7.3 line 626
- CVSS 7.9
- 现状:"server 永远接收(LWW 是按 server_updated_at 排序,旧版本仍接收只是没用)"。用户的本地编辑被对方覆盖时,**没有任何痕迹保留**。
- 修正:
  - 客户端 PUSH 时带 `base_revision`(读取时看到的 revision),服务端 conditional write:`base_revision == current` 才接受,否则返回 `409 { server_revision, conflict_blob }`。
  - 客户端展示冲突,让用户选合并 / 覆盖 / 保留双份。
  - 或:服务端保留 "conflict shadow"(每次被覆盖的 loser 单独存 30 天),Console 设置页可恢复。

#### H-06 Outbox 合并 "同 entity 只留最新" 破坏依赖操作
- 位置:§5.6 FR-SY-34 line 321
- CVSS 7.4
- 现状:回放时"同 entity_id 的多条 op 合并(只保留最新一条)"。问题:
  - `create todo A → assign label L to A → delete A`。合并掉中间 → server 只看到 "delete A",但 `label_assignments` 表的 row 可能已经先 push 了,造成 dangling reference。
  - `create label L → assign L → delete L`。合并后只剩 delete,但 assignment 引用了一个不存在的 label。
- 修正:
  - 按实体 DAG 拓扑排序合并,不能跨依赖跳过。
  - parent delete 触发 cascade 必须在客户端就生成对应 mutation(`label_assignments` 的对应 row 也加 tombstone),并保证两个 mutation 在同一 commit 批次原子上传。
  - 服务端按 commit_seq 单调消费,跨表强引用约束(虽然 RLS 不能强制 schema 级 FK,但客户端按规则消费)。

#### H-07 PUSH 无 idempotency key,网络抖动重试会产生重复 mutation
- 位置:§5.9 line 348 FR-SY-46(原子 batch)、§7.3 PUSH 协议
- CVSS 7.6
- 现状:`FR-SY-46` 说 batch 是 atomic,但**整 batch 重试**没有 idempotency key 防重放。client 发 batch → server 处理成功但 ACK 丢包 → client 超时重发同一 batch → server 当新数据接收,产生重复 revision。

  - server 接到重复 mutation_id → 返回上次的 result(true idempotency)。

#### H-08 RLS 只校验 account_id,未校验 originator_device_id 是否注册/未撤销

## 协议正确性问题(分布式系统视角)

当前协议**不是一个可证明收敛的最终一致系统**,而是 "client 写、server 戳时间戳、谁最后到谁赢" 的覆盖式同步。三个根本性缺陷:

### P-01 没有 causal ordering,跨实体依赖无法保证一致
PRD 通篇没有 vector clock / lamport timestamp / commit_seq 的设计。考虑场景:
- 设备 A:`create label "重要"` (e1) → `assign label "重要" to todo X` (e2)
- 设备 B(同时):`delete label "重要"` (e3)
- 服务端按 `server_updated_at` 排序:可能是 e1 → e3 → e2,**最终状态:label 被删除,但 label_assignment 仍指向已删除 label_id**(dangling reference)。客户端 UI 会显示 "X 有一个未知 label"。
- 修复方向:每个 mutation 带 `causal_dependencies: [previous_seen_revision_for_each_referenced_entity]`,服务端拒绝依赖未满足的 mutation;或客户端在 reconcile 时检测 dangling reference 并清理。

### P-02 没有 conflict-free 数据结构,文本类实体(notes)的多端编辑必丢
对 `notes.content_md` 这种长文本,LWW 是产品上灾难性的(用户编辑 30 分钟的笔记,被另一台手机的小修改盖掉)。PRD §1.2 把"不做 CRDT" 列为非目标,但**notes 是 v1 核心实体**,必须做出选择:
- (a) 笔记 v1 不支持多端编辑(单设备绑定,其他设备只读)。
- (b) 笔记 v1 走 LWW + 强 UI 提示 + 自动 backup 旧版本(参考 Bear notes)。
- (c) 笔记 v1 走简化 CRDT(Yjs minimal,server 只存 update ops 而非整 row)—— 但与"整 row 加密" 冲突,需要重新设计。
- 这个决策必须在 Phase 0 子阶段 0.3 之前定,否则 Phase 5 改不动。

### P-03 没有形式化的收敛证明 / 模型检查
LWW + tombstone + outbox 合并 + idempotency 这套组合在哪些 ordering 下能收敛、哪些 ordering 下不能,PRD 没说也没验证。Phase 5 验收 §10.2 的"30 分钟数据 100% 一致" 是行为级测试,不是形式验证。
- 建议:用 [TLA+ specification](https://lamport.azurewebsites.net/tla/tla.html) 或 [Stateright](https://github.com/stateright/stateright) 把同步协议建模,跑模型检查(2-3 个设备 × 短序列 mutation)。这在 Phase 5 末做最经济。

### P-04 服务端无强一致写路径,batch atomicity 仅靠 Postgres transaction
FR-SY-46 "batch 50 record atomic" 依赖 Postgres 单 transaction。但 Supabase Realtime 是 logical replication 推送,**realtime 推送到订阅端的顺序不保证与 transaction commit 顺序一致**。如果一个 batch 跨多条 record 触发 realtime,订阅端可能先看到 record_N 的通知再看到 record_1。客户端按 server_updated_at 排序应能容忍,但**需要在测试中显式验证 realtime 乱序到达下 reconciliation 正确**。
