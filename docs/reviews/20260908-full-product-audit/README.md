## 重点回答：离开、关页、断网后会怎样

以下“恢复”均以同一浏览器、同一 origin、数据已成功保存且未被清理为前提。

| Feature / 场景 | 关页后与重开后的当前表现 | 后续应达到的结果 |
|---|---|---|
| **Time Tracker** | 开放 segment 已持久化；关标签再开实测恢复 Running，按开始时间补算。跨午夜分配、未来记录和多标签并发仍有缺陷 | 按当地日期边界拆分时段；恢复显示离开时长并允许修正；单活动会话和幂等结束 |
| **Pomodoro** | 当前 running/paused 仅组件状态；刷新实测从 24:59/Focusing 回到 25:00/Ready。路由卸载也会丢失本次会话 | 保存活动会话与 deadline；启动即落盘，重开补算、一次结算，显示恢复选项 |
| **Meditation** | 每次 interval 回调加 1，后台节流会少算；关页丢当前会话；显示到零也未完成停音/记录闭环 | 改为绝对时间，保存会话；到期停音并记账，明确是否恢复播放 |
| **Countdown / 时钟** | 目标日期/偏好保存，重开按当前时间重算；没有到期通知 | 明确日期/时区；如需提醒，另定义可靠调度能力 |
| **Tasks / Habits / Calendar / Boards** | 已提交数据可恢复；草稿不全保留。“今天/明天”、当地日期和午夜刷新有错误 | 真实日期查询，统一时间语义；提交确认/草稿恢复，保存失败不假报成功 |
| **提醒 / 勿扰** | 多处只保存设置，没有执行消费者；关页无系统提醒服务 | 未接线时显示能力限制；如承诺关页提醒，需要调度、权限、投递回执及重试 |
| **Board 自动化** | 仅页面 effect 或手动执行；关闭后不执行，重开也只处理活动看板，且有一天一次限制 | 明确页面触发范围；可靠自动化需持久计划、幂等 occurrence 和执行历史 |
| **AI** | 离开 AI 路由主动 abort；保存过的文本可恢复，当前请求/队列/待确认动作不续跑 | 显示 interrupted 状态及重试；若要求离页完成，先服务端持久化 job，再执行与订阅结果 |
| **记账周期规则** | 规则保存，当前依赖手动执行，不会无人打开页面时自动入账 | 明确“手动应用”；自动记账应有计划、去重和执行回执 |
| **离线重新打开网页** | SW 只预缓存两个 HTML，未覆盖 JS/CSS；代码模拟显示 HTML 成功而 JS 失败 | 版本化资源清单；真实浏览器离线冷启动、旧版本更新、失败回退验收 |
| **Mac 关窗/退出** | 不能把托盘存在当后台计时/通知存在；当前通知依赖 Webview 轮询，退出后停止 | 原生持久调度；区分隐藏、销毁窗口与退出；SQLite 提交确认与恢复记录 |

“重开可补算”和“离开后准时执行动作”应写成两条独立产品承诺。前者通常可以用持久开始时间/deadline 实现；后者需要真正的后台或系统调度。不要依赖 `beforeunload`、每秒 tick 或未等待的异步写入作为可靠性保证。

## 最高优先级与可验收的修复批次

P1 为用户状态、关键行为或发布通路问题；P2 为体验、一致性或需要验证的局部风险。暂停模块的安全缺口是**开放前门槛**，不等于已确认线上遭利用。

| 批次 | 需要解决的问题 | 最小验收证据 |
|---|---|---|
| A · 状态与时间正确性 | Pomodoro 活动持久化；Time Tracker 日界；Statistics 实际时长；Tasks 日期与 Board 关联；Meditation 完成 | 启动→切路由→刷新→关页→重开；23:50→00:10 分配；25min 配置早停1min仍统计1min；关联移动/完成不丢 |
| B · 本地账户与保存可靠性 | auth/device 共库但分别初始化 store 导致 NotFoundError；业务数据/key 未按账号隔离；删除 registry 漏记账/指标；写失败无反馈 | 新 profile 两种初始化顺序；A退出/B进入无A数据；quota/禁用存储/多tab删除失败可见且可重试；旧数据迁移不丢 |
| C · 发布与运行闭环 | CF认证失败、生产版本未知、构建配置来源不一致、PWA资源不完整、RUM未完整发送 | 预览成功与 deployment receipt；发布SHA可见；真实浏览器离线冷启动；错误事件在实际接收端可查 |
| D · 高频 UI/UX | Switch变形、工具栏挤压、核心动作不在首屏、样例/未实现入口混淆、弹窗/IME/键盘不齐 | 桌面与390px、中文长文、浅深色、大字号；全流程键盘；空/加载/错误/保存失败/恢复状态截图 |
| E · 工作流事实对齐 | 漏19份日志、漏3个AI roadmap、11个迭代旧状态、缺9份canonical PRD、当前/历史测试混合 | 每feature能追到实现/测试/部署各自SHA；解析器fixture；SKILL源元数据与生成补齐分列；fresh只描述采集时间 |
| F · 原生/后端开放前 | SQLite异步提交未等待、native提醒轮询、sync transport缺失；后端请求context验签/设备授权薄弱；Admin模拟写入 | 真机重启/崩溃/睡眠；真实两设备正负同步；真实DB并发/RLS；服务端持久审计；签名、公证、更新门禁保持独立 |

Sync 请求 context 的本地探针接受无 Authorization 的 fallback 及无效签名 payload，是明确的上线前修复信号；本次没有对生产服务做越权访问，也未验证其实际部署。账号云同步仍按项目规则暂停，不应为修 Web 时间恢复而绕过 D4 或启动整套云同步。

UI 比较依据是当前已跟踪的 `web design/DESIGN.md`、项目 PRD 和 Apple Reminders / Linear / Trello 官方资料，详见 05 的直接来源。采用可读性、主动作位置、视图一致性和明确执行范围，避免把通用美化 skill 的装饰性建议直接套入生产力工具。

## 本轮结论的使用方式

按上述 A/B/C 优先批次转为独立可验收任务，再推进 D/E；F 保持各模块的开放门槛。每个修复应关联本报告的具体 feature 和证据，记录“修复后当前 SHA 的验证”，保留本次基线报告不回写成已修复状态。界面美化、数据正确性、后台能力扩展和发布工作应分别验收，避免一个总体完成百分比掩盖差异。
