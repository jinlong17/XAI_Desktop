## 6. Journal N/N+1 protocol, crash cuts and exact recovery

Before edit acquisition, qualify storage read/write/readback, owner/marker/tombstone and the all-writer protocol. Unsupported coordination or initial durability unavailable refuses editing acquisition. Every accepted onChange records newest full text durably and reads it back before Draft saved/close-safe acknowledgement. Canonical consolidation may be deferred only after this capture. Accepting keystrokes freely and awaiting an IndexedDB/Web Lock later does not prove latest-input direct-close survival; blur/unload/debounce cannot supply the sole durability point. A post-ack crash/restart also needs actual platform evidence; localStorage method return alone is not process-crash/fsync proof.

Canonical transaction under one admitted dataset serialization:
1. Capture and reread source plus journal, live owner/marker/tombstone, operationId and sequence. Validate full source without destructive normalization.
2. If canonical raw differs from captured base, refuse and retain local latestText, full baseRaw and newer externalRaw with visible conflict. Same-slot and other-slot changes both require a reviewed merge/rebase choice, never stale whole-blob last-write-wins.
3. If equal, apply only the F2 diary slot, preserving every unrelated field/key. Write canonical and verify exact readback. After-success check-in events apply only to successful logical check-ins; hydration/retry/journal capture emits no duplicate recorded event.
4. Canonical readback for N acknowledges N only. If N+1 exists, keep it captured/pending and do not clear/reassign it. Cleanup may remove/compact only the exact entry whose operationId,N and acknowledged canonical bytes still match; no unconditional journal remove.
5. Persist cleanup acknowledgement or retain cleanup-pending. If canonical write succeeded but cleanup/readback failed, recover by checking exact canonical acknowledged bytes; don't replay an older diary. Uncertain outcome is not Saved and stale reconcile tokens never authorize another sequence.

| Failure/crash cut | Required recovery result |
| --- | --- |
| Before durable capture or capture/readback failure | Not saved; latest attempted text retained/recoverable where available; mutations/departure do not claim success. A forced close losing accepted input remains a failing HAB-03 case, not waived by warning. |
| Journal N captured, canonical untouched | Reopen correct owner/habit/month with exact text N and source health; no false canonical Saved. |
| Journal N captured, N+1 input arrives while N consolidates | Durable latest full text N+1; acknowledgement/cleanup N cannot clear N+1 or route it to another editor. |

## 7. Coordination feasibility and bounded lifecycle participation

The proposed long-lived pre-acquired editor lease can explain synchronous capture, but current source does not prove it safe. Non-atomic localStorage lease/CAS, StorageEvent/BroadcastChannel-only ordering and indefinite shared lifecycle leases are rejected as proof. Existing short account-shared/key-exclusive async transactions are useful but not sufficient for a synchronous onChange plus two physical keys. Editing while only a dataset lock is held permits tombstone/check/write races with lifecycle writers; adding a tombstone reread alone is not atomic with the write.

Candidate lock order is account lifecycle authority → Habits dataset covering canonical AND journal → editor/sequence operation. Export needs a consistent point-in-time read under that same authority or an explicitly versioned non-atomic export; reset/migration/delete need exclusive lifecycle/disposition. No new path may nest the current pref-key lock against itself or acquire dataset then lifecycle. All sync entrypoints/global reset must join or visibly refuse; “all converted” is a future admission gate.

Engineering alternatives remain proposals:
- Pre-acquired synchronous capture lease: admit only if actual platform tests prove acquisition before editable input, owner fencing, short bounded lifecycle hold/revocation and release on pagehide/hidden/unmount/crash, including a suspended/unresponsive holder. Cooperative event revocation alone is insufficient. A permanently held lifecycle shared lock is blocked.
- Transactional journal/backend or a coordinated authority: can give canonical+journal serialization, but must prove latest accepted input survives direct close before asynchronous completion. This is a different storage/API impact and cannot weaken HAB-03 into a debounce window.
- Separate capture/consolidation protocol: any design that avoids a long lifecycle hold must prove deletion/tombstone race cuts, paired recovery ownership, reset completion and stale write refusal. Unregistered per-tab dynamic key families are not admitted escape hatches.

No option is established as viable by this document; implementation stays BLOCKED on proof. Lock-unavailable must promptly refuse edit acquisition. A lifecycle request gets an explicit settled/refused/recovery-required outcome or a cancellable visible pending handle, rather than indefinite silent wait. Bounded acquisition/hold/revocation/recovery thresholds must be specified as reviewed engineering parameters and measured against real suspended/crashed holders; this report invents no owner timeout or data-loss waiver. Refusing reset forever is not evidence of authorized reset/delete liveness. If release/liveness cannot be proved, preserve recovery and report blocked rather than implement the candidate.

Reset: coordinate draft capture/export/explicit disposition, fence queues, apply canonical+journal transition with exact readback and durable partial-failure receipt; preserve valid-empty intent/no reseed. Global defaults events remain accurately attributed and cannot announce paired completion early. Delete: respect server-confirmed/unknown-outcome phases and captured owner; tombstone precedes destructive work; resume validates raw receipt, removes all owned generations/journal/candidate records, retains tombstone and protected unassigned archives/device data, secret/auth cleanup separately, completion only after its admitted chain. Migration: copy journal with canonical or explicitly quarantine it, never copy a stale live lease; validate fixed key, archive both source sets, commit marker last, restart reauthorization and exact previousRaw/null rollback. Export: canonical+journal consistent snapshot, secret exclusions and actual file evidence. App departure: reserve existing first intent, combine participants without changing rail→Appearance→Settings ordering, authorize only after current capture recheck; logout revokes visibility but is not deletion.
