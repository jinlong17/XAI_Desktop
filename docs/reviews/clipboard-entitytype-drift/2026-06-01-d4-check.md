## Assessment (honest severity)

**Not an active data leak.** The plugin's only write path (`RepoAdapter.save()`) explicitly stamps
`syncScope: "device-local"`, so live clipboard records are device-local in practice, and the sync
runtime is paused anyway.

**Real correctness/governance gap.** (1) The device-local invariant is held by *adapter convention*,
not the *central* `assertRepoRecord` guard — the guard's clipboard-specific lock keys on
`clipboard.item` and never fires for the runtime's `clipboard.entry`, so any future non-adapter write
path (migration, direct `repo.put`, a new code path) would bypass the safety net. (2) The registry
and the runtime disagree on `entityType`, `schemaVersion`, and field shape, so the canonical
`clipboard.item` record shape and the live `clipboard.entry` shape are not interchangeable.

## Reconcile options (decide before landing — needs operator unfreeze, plugin line is P2 PAUSED)

- **Option A (align runtime to canonical):** make the plugin use `clipboard.item` and the
  `ClipboardEntryEntity` shape; keep the matrix + guard as-is. Largest plugin diff.
- **Option B (align registry to runtime):** make `clipboard.entry` the registered `entityType`,
  update `RepoEntityTypeMap`, the matrix, and the `assertRepoRecord` device-local lock to key on
  `clipboard.entry`; reconcile the field shape. Smaller plugin diff, touches central registry.
- **Either way:** generalize the `assertRepoRecord` device-local lock to enforce scope from the
  scope matrix (not a single hardcoded string), and add a test proving the clipboard runtime record
  is outbox-excluded.
