# Settings durable deletion — implementation contract

Astra, Web, 2026-09-09. Approved bounded implementation direction extending `0b3a043`, based on fixed c201a1d storage source, parent Settings baseline `33832b1` and the two new deletion admission FAILs. Terra can implement storage API and Settings caller together. This is not acceptance, deployment or authorization to close D2/AI-02/REL-05. No new receipt physical key or backend change is needed.

## One shared receipt contract

Put the strict decoder, identity matcher and physical deleted-key derivation in **storage**, exporting them for Settings. Storage must not import Settings or AI Chat. Preserve the existing deleted key and version 1/2 compatible fields: version, accountId, account/demo kind, nonempty business generation, valid phase, timestamp, and version-2 captured authGeneration (version 2 is account-only; version 1 cannot silently carry authGeneration). Validate that the decoded owner/kind matches the physical key. Invalid JSON, primitive/legacy `1`, incomplete shape and mismatched owner/kind/generation never independently authorize cleanup. Parse failures are recovery refusal, not absence.

Separate an initial current-owner operation from durable resume. A current-owner begin captures owner before enqueueing, acquires that account's exclusive lifecycle lock, verifies complete matching marker/tombstone state, and durably writes a complete deletion intent before destructive work. For server-confirmed deletion that completed after A→B, use the existing captured confirmed-deletion context and its durable intent; do not invent permission by resolving mutable current B, activating A or fabricating a live epoch. Preserve the orchestrator's rule that unconfirmed server/network outcomes do not start local erasure. Begin itself becomes awaited wherever its durable write can wait or refuse.

The separate `accountDeletionIntent.ts` record is explicitly `server-outcome-unknown`; it is **not** a deleted receipt and must never authorize resume by itself. Preserve its operationId/raw identity through the original request. Only the matching in-flight orchestrator branch that actually received server success/already-deleted (or the explicitly supported mock-auth branch) may publish the full deleted receipt for captured A after A→B, under the short account-exclusive check. Expose that narrowly named confirmed-begin operation separately if needed; do not require reactivating A. Recovered unknown outcomes stay discoverable and non-destructive.

The current helper that writes legacy `1` must not grant arbitrary resume privileges. Prefer emitting the same complete receipt before first deletion so its subsequent partial/idempotent retry has durable proof. If test expectations currently assert literal `1`, only that format assertion may become a stronger decoded matching-receipt assertion; retain actual tombstone preservation, partial failure, retry removal, scope isolation and truthful-result assertions, with the original logs retained. Existing unproven legacy `1` after reload requires recovery refusal, not silent conversion when its marker is gone or conflicting.

## Proposed storage API and lock boundary

Add a named async resume operation, for example `resumeAccountLocalDataDeletion(expectedReceipt, options)` with storage/lock seams and an expected raw receipt snapshot. Return an explicit success including the freshly persisted receipt/raw token, or a typed refusal (`lock-unavailable`, `receipt-changed`, `recovery-required`, `storage`, as appropriate). Never treat an arbitrary object supplied by the caller as the durable proof.

Inside the account-exclusive lock, in order:

1. Re-read the **physical** deleted receipt. Strictly decode and bind it to expected account/kind/business generation/version/authGeneration. Recheck its raw token and phase; an unrelated replacement, even for the same account, cannot inherit the old operation's authority.
2. A present generation marker must be complete and match the receipt generation. An absent marker is allowed only for a complete, matching persisted deletion intent in a legitimate recovery phase. A corrupt or conflicting present marker refuses; any string tombstone is insufficient. The new public admission FAILs must preserve all bytes.
3. A valid durable A receipt may finish A when B or locked is current. This is the explicit resume API's exception; do not relax current-owner checks in ordinary pref/autosave/scoped/canonical writes. Derive all prefixes, secret owners and auth generations from the receipt and leave B/device/unowned bytes untouched.
4. Erase the captured account's local records while retaining its receipt. Verify completion before publishing `local-data-cleared` under this same exclusive lock, using the expected current receipt/raw token. A physical error or phase-write error refuses and leaves durable recoverability. Marker removal during a partial pass must not make the next valid resume impossible.
5. Return the actual persisted phase/token. Already complete matching receipts return idempotently without repeating downstream cleanup; never regress complete → local-data-cleared or overwrite a replacement intent. A concurrent legitimate phase advance may be returned as observed progress or a retryable stale-token result, but must not be mistaken for authority to continue stale work.

There is no synchronous fallback on lock failure. Use the existing account lock name without generation and preserve account-before-domain ordering. Storage may expose a short exclusive receipt-transition helper so Settings does not perform uncoordinated phase writes itself. Account cleanup owns its already-held raw context; it must not recursively ask an ordinary shared writer to mutate beneath the exclusive lock.

## Settings execution, concurrency and participants

`accountDeletionRecovery.ts` reuses the shared storage decoder/type and awaits the new begin/resume/phase results. `useAccountDeleteOrchestrator.ts` awaits intent persistence before starting cleanup and reflects refusal as recoverable failure. `AccountDeletionRecoveryNotice.tsx` retains its explicit awaiting and visible failed/retry state. Do not substitute current-account `deleteAccountLocalDataAccount(restoredEpochMinusOne)` for the durable API.

Serialize compatible-client recovery coordinators for the same account through a distinct, generation-independent **recovery workflow lock** (plus optional in-page single flight), acquired before short account-exclusive sections. This prevents two tabs from independently running the same phase and participant concurrently. Ordinary writers do not take this workflow lock. The order is recovery → account → any local domain lock, never account → recovery. After acquiring workflow ownership, reload the persisted receipt rather than trusting the UI's old object.

Release account/domain locks before awaiting secret cleanup, auth cleanup or network work. A recovery workflow single-flight lock may remain held solely to serialize that recovery; it is not the account lifecycle lock and must not block unrelated current-account writers. Do not wrap provider requests in the account lock or recursively invoke a participant that takes the recovery lock. If a participant needs the account lock for its own local secret operation, it can acquire it after the cleanup section has released it; ordinary secret-writer coordination is still a later D2 ownership slice.

Before each asynchronous participant, and after every await before the next participant or phase publication, re-read and compare the current durable receipt identity/token. Stop on replacement or unexpected phase changes; never overwrite a newer intent or regress phase. Secret cleanup and captured auth cleanup use A's persisted original identifiers, including authGeneration, never whichever auth session is active now. Preserve existing v2 refusal when captured auth cleanup is unavailable. Re-enter a short exclusive receipt transition for complete publication and recheck the token there. UI success requires that final transition to succeed.

A completed matching receipt is an idempotent no-op on later retries. Partial secrets/auth or final metadata failure keeps the receipt recoverable and may repeat idempotent captured-owner cleanup after a crash; this is not exactly-once external side-effect delivery. The workflow lock prevents concurrent compatible live coordinators, not old arbitrary JavaScript or process-crash duplication. No new provider/network implementation is requested in this batch.

## Fixed acceptance cases for this slice

- Retain parent Settings original two lock/order/refusal failures and A→B marker-removal retry control. Lock pending means no local erasure, no phase advance, no secret/auth callback; unavailable lock refuses with unchanged bytes/receipt.
- Preserve the foundation original 14 business oracles and the two new admission refusals, C 37 and D1 shared 8. Missing marker + valid matching receipt resumes; missing/corrupt marker + arbitrary tombstone refuses. Conflicting generation cannot be overridden by legacy `1` or mismatched structured metadata.
- Restore a complete receipt after reload with B/locked current; finish only A, including partial removal retry and repeated complete no-op. Keep captured authGeneration and no B navigation/auth changes.
- Queue two independent recovery calls for the same receipt; assert monotonic phase and no parallel duplicate participant dispatch. Replace raw receipt/phase, business generation or authGeneration during queue/secret/auth waits; the old continuation refuses further publication/participants and leaves the new bytes intact.
- Fault real local remove, secret/auth participant and final receipt setItem separately. Preserve truthful failure, retryable metadata and no complete phase until all required work has succeeded. Native lock and current-client coordination evidence must remain clearly distinct from mocked participant outcomes.

Implementation ownership: storage `accountDataLifecycle.ts`, a shared receipt helper/export and focused tests; Settings `accountDeletionRecovery.ts`, its orchestrator begin/await call site and recovery tests. Change the notice only if its actual async result presentation needs adjustment. Do not change unrelated Tasks/Board/Calendar product paths.
