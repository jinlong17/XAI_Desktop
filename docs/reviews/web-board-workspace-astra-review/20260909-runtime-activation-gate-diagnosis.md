# Astra: actual Web runtime readiness for the canonical activation gate

**The current Web runtime does not implement a verifiable general-purpose legacy-client drain/upgrade gate.** B–D representation and current-version writer coordination can proceed, but the first receipt-envelope activation in existing physical keys must remain disabled outside a proven controlled rollout. Neither the present Service Worker nor deployment metadata proves that old writers have stopped. A public transparent migration of all existing browser populations cannot currently meet the `501feb7` preservation contract.

This is a bounded source diagnosis, not a deployed-runtime result or a new-protocol race reproduction. Source baseline: `b2df4ce7ca5dfbac6cce12d3eb928c0aa0819374`. Reviewed `apps/web` bootstrap/SW/build/headers/deploy workflow, release identification, relevant account gate, and rollback guidance. These Web paths had no diff against that baseline during review. Terra's concurrent storage B1 files were left untouched; legacy storage behavior was read with `git show b2df4ce:…`, not inferred from the uncommitted implementation. No production URL, deployment console, real browser profile, credentials or live headers were queried. No build/deploy or product edits were performed.

## Concrete gaps and limits

**Mixed executing versions remain possible.** `skipWaiting` changes the active worker promptly; `clients.claim` changes control of requests, not the already running application JavaScript. The documented SW lifecycle explicitly distinguishes installation/control from page loading and warns about mixing versions managing shared storage. Removing unconditional `skipWaiting` can help a controlled cohort wait for old controlled clients to leave, but does not identify every uncontrolled legacy page or prove all same-origin writers have upgraded. [Browser lifecycle reference](https://web.dev/articles/service-worker-lifecycle).

**An old offline shell has no version admission check.** The worker source/cache name does not change with the application build in the inspected pipeline. If the SW bytes remain identical, a new app deployment does not by itself produce a new SW install; the cached shell can still be the one installed earlier. Navigation's network result is not written back into that shell cache. Offline fallback may therefore return old HTML; whether all its assets are still available depends on actual browser/cache/deploy state. This is a source-derived stale-entry path, not a claim that a live production profile was observed executing it. Worker updates are based on script changes, rather than Pages commit metadata. [Update lifecycle reference](https://web.dev/articles/service-worker-lifecycle#updating_the_service_worker).

**Locks cover participating clients, not arbitrary old writes.** Web Locks coordinate lock requests; localStorage writes are not automatically routed through that API. An old direct `setItem` bypasses the new writer's lock. Version metadata, a BroadcastChannel silence timeout or post-write StorageEvent observation cannot prevent that overwrite or reconstruct erased receipts. [Web Locks specification](https://www.w3.org/TR/web-locks/).

**The first bridge release cannot retroactively add cooperation to pre-bridge code.** A server auth logout, fresh deployment, claimed worker, or waiting some number of days does not prove an offline/suspended old page has stopped writing its local store. New bootstrap checks only constrain builds that include those checks. This is the key limitation for a universal same-physical-key migration.

## Smallest useful implementation proposal — not implemented or newly authorized here

Keep existing canonical physical keys and the approved domain-plus-receipt envelope. Do not introduce a second journal key or silently switch backend. Add a separate rollout gate; it must not be conflated with the per-key concurrency lock.

1. **Keep envelope activation off by default.** B1 dual-read/codec work and subsequent all-writer compatibility may be tested in disposable controlled profiles. The first writer that would upgrade a legacy key must require explicit compatible-runtime admission. No missing admission, offline check failure or unknown client may silently mean approval. A local flag is only new-client policy, not proof that old clients are absent.
2. **Ship a bridge while retaining the legacy data representation.** Proposed owners: `.github/workflows/deploy-web.yml`, `apps/web/vite.config.ts`, bootstrap, SW registration/worker, and a small runtime compatibility module. Embed a required build id and storage protocol capabilities into app/SW plus a small deployment compatibility manifest. Make its cache policy explicit and ensure normal navigation, restored sessions and offline bootstrap either load a proven compatible build or visibly withhold writes. Gate business mounting and side-effectful imports before storage writers can start; merely adding an informational banner after `main.tsx` renders is too late.
3. **Implement a graceful current-client update protocol.** Compatible clients expose build/protocol id, active editing/draft state, quiesce acknowledgement and explicit save/export/reload actions. Use SW messaging/client enumeration or BroadcastChannel for participating clients, but never treat nonresponse as absence. Recheck admission on resume and before canonical writes. If the chosen transition policy requires a fresh online compatibility lease, offline writes must visibly pause until admission returns; that is a product tradeoff to approve and test, not a transparent change.
4. **Make SW assets/version transitions explicit.** Generate build-scoped shell caches; remove only owned obsolete caches; prevent stale HTML fallback from mounting a writable incompatible app. Make HTML/SW/compatibility-manifest revalidation policy explicit. Do not use unconditional forced takeover/reload while drafts may exist. Natural SW waiting is useful only within its controlled-client boundary; a new page waiting behind the old worker may also need all app tabs closed before activation. None of these mechanisms alone proves that a pre-bridge writer is gone.
5. **Use a controlled activation ceremony for legacy populations.** First export/confirm saved work, then actually terminate or navigate away every old context in the chosen browser profile/partition; reopen a verified bridge-compatible build without restoring incompatible cached/session content. Record build identities and the storage/profile boundary, then activate migration. This is implementable for managed/local pilot profiles. A user clicking “I closed other tabs” or an empty new-protocol heartbeat list is not universal machine-verifiable evidence. For unknown public populations the activation must stay blocked.
6. **Constrain rollback and reentry.** Only compatible builds may be redeployed against migrated keys; update the specific rollback gate before rollout. Test old cached navigation, session restore and supported offline modes. If an incompatible writer can still reenter, the release gate fails even when every current-version concurrency test passes.

This bridge is a future useful baseline, not a claim that it solves the first legacy population automatically. B–D can finish their compatible-client guarantees while the public activation gate remains open.

## Decision returned to the parent

- **Recommended now:** continue the approved B–D implementation with activation disabled except in explicitly controlled verification profiles. Assign the bridge/runtime gate as a separately scoped Web task with the paths above and a before/after old-build test plan. Do not quietly add it to Terra's current storage B1 ownership.
- **Controlled rollout option:** limit initial activation to demonstrably drained/upgraded profiles and state that supported population precisely. This can provide a concrete pilot path without changing canonical keys, but it is not a universal public-Web guarantee.
- **Universal public rollout requirement:** if the operator requires transparent safety for arbitrary already-running/offline old clients, the present same-key/client-only design has no demonstrated way to enforce it. Keep public activation/full closure blocked and return for architecture review of an enforceable isolation/authority boundary. No physical-key/backend change is approved or implemented by this diagnosis.
