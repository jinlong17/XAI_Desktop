Astra, non-author; Web; 2026-09-09. Product fixed to `32415295f212c48d69dbd29387635422392a8888`, against `7b95133` ordinary-writer contract. **Not accepted: six correct FAIL assertions identify four remaining defect groups.** No product edits or audit-item closures.

## Findings and minimum repair ownership

### P1: detail edits and their retries lose the original target baseline

`TasksModule.tsx:352–378,1257–1304`: the detail panel intentionally retains form values when the same task ID changes, but `handleDetailSave` checks/persists against the current `taskCols`. Open t1, type a local draft, observe an external replacement through a real StorageEvent, then Save. The external title is overwritten by the stale form and no alert remains. Repeating this after an initial quota failure produces the same overwrite. Both independently asserted cases fail; the external record contains a valid canonical revision and retained receipt.

**Fix ownership: TasksModule detail session, save callback and locked precondition.** Capture the opened task/source baseline with the draft, retain it through quota and subsequent retries, and pass it into the locked mutation. An observed same-ID replacement cannot implicitly authorize rebasing the stale patch. Compare the expected entity or conservatively retain the original dataset baseline; preserve the latest receipt metadata. Allow latest local form edits after failure while retaining the original persisted baseline. Keep valid unchanged-target save and receipt-only revision behavior usable. The global checkbox recovery already retains its original baseline and passes unchanged; do not regress that path.

### P1: removal of a pending edit's target hides the unsaved draft and recovery

`TasksModule.tsx:179,395,559–564,1257–1283`: the detail is derived from `findTask(taskCols, editingTaskId)`, so a StorageEvent deleting the edited target makes `located` null. Its panel returns null; the top-level recovery is also suppressed because `editingTaskId` remains truthy. Our actual UI queues Save with “Keep missing-target draft”, removes that target externally, then releases the lock. Storage is correctly preserved, but panel, alert and visible draft are all absent. The storage refusal is not sufficient UI recovery.

**Fix ownership: TasksModule/TaskDetailPanel session snapshot and failure presentation.** Retain the editable snapshot independently from the live target lookup. On a missing/replaced target, display conflict/recovery with the latest local draft and export/close access, refuse silently recreating the task, and do not switch draft identity to another task. Closing intentionally can release the session; an external disappearance cannot be treated as a successful dismissal.

### P2: old bulk deletion clears a new selection and detail session

`TasksModule.tsx:326–330`: after awaiting deletion of the captured selection, `setSelectedIds(new Set())` clears every current selection, and the captured `editingTaskId` condition calls `setEditingTaskId(null)` even if another task is now open. Actual UI: select/open t1, queue bulk Delete, close it, clear selection, select/open t2, release t1 deletion. t1 is correctly deleted, but t2's selection and detail both disappear.

**Fix ownership: TasksModule bulk operation completion.** Remove only successfully deleted captured IDs from the current selection, and condition any editor close on the still-current editor/session belonging to a deleted target. Use a session/selection token or functional guarded updates. Do not weaken the existing delayed single-detail deletion and composer session protections.

### P2: list/tag deletion leaves orphan references in supported completed storage

`TasksModule.tsx:140,308–319,736–750`: list reassignment builds IDs from `activeTasks = taskCols.flatMap(col => col.tasks)`; tag removal likewise maps only `col.tasks`. With a valid normalized `col.completed` task referring to Inbox/Study, actual Delete list / Delete tag removes the metadata, but leaves `listId:'inbox'` / `tags:['study']` on that task. Two assertions fail. The task's completion state and durable receipts are otherwise retained. Completed storage is a supported domain, also covered by existing package completion tests; it cannot be discarded as an invalid legacy fixture.

**Fix ownership: TasksModule cascade ID inventory and tag helper (or existing pure reducer helper if factored).** Include both active and completed arrays, preserve completion/timestamps/IDs and unrelated metadata, commit the task-reference change before deleting metadata, and stop metadata deletion if that commit fails. This does not require cross-key atomicity or rewriting the shared canonical engine.
