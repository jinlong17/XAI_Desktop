## Verified behavior and source assessment

- A physically absent dataset initializes only on the supplied initializer and commits data plus receipt with one `setItem` to the existing account physical key. Valid legacy data is retained alongside the new item. Present JSON null, envelope null, wrong domain shape, malformed JSON/receipt or unsupported version never seed or write.
- Quota failure preserves exact prior bytes and leaves the identity retryable. Successful retry commits once; subsequent replay preserves bytes. A discarded caller response after commit replays without another mutation/write. This models lost acknowledgement, not an actual browser process crash.
- Receipt lookup precedes target mutation: the prepared deleted-target replay succeeds without invoking its throwing mutator, including after a new same-account scope. Changed semantic content conflicts. Known receipt replay survives full receipt capacity and maximum revision in the package checks; new identities are refused without eviction. `__proto__`, `constructor`, and `toString` identities remain safe own receipt entries.
- Both current domain and mutator output are validated. Source also re-parses the exact encoded candidate and checks its domain before storage mutation. Invalid outputs/targets and read denial fail without committing a receipt. A failure to acquire Web Locks or an absent lock API does not enter an unlocked mutator.
- Source acquires its per-dataset lock before checking the captured owner, deletion tombstone and full generation-marker shape/generation, and performs the check again immediately before the sole write. Independent cases change/remove the persistent marker, create a tombstone, or switch account during lock acquisition and observe refusal with original bytes preserved. Author final-check assertions were independently rerun too.
- The deterministic duplicate-request lock test uses the actual primitive twice, sees the same lock name, and proves one mutation/write. It does not prove native lock scheduling, current UI participation, old-version participation, or account migration exclusion.

## Exact representation limits

Signature length is at most 16,384 JavaScript string code units; a JSON string payload of 16,382 ASCII characters reaches that limit and one more is rejected. Plain object keys sort recursively, arrays retain order, and unsupported values/cycles/sparse arrays reject. The primitive expects already validated semantic operation fields: excluding transport epoch/attempt/requestedAt remains a subscriber obligation.

Channel and request ID each permit up to 192 code units; the escaped JSON tuple must additionally fit the 512-code-unit stored receipt ID limit. Consequently, heavily escaped valid-length parts can still be rejected when their composite exceeds the storage limit. C intentionally widens B1's stored receipt-key bound from 192 to 512 to carry that composite. The earlier B1 reviewer test's raw 193-character-key rejection is superseded by this explicit representation rule, not evidence that old data was rewritten. Existing shorter IDs remain readable; raw B1 logs remain intact.

The encoded record limit is exactly 4,000,000 JavaScript string code units, not a measured UTF-8 byte limit or a promise of browser quota availability. An independently constructed exact-limit envelope commits, replays without another write, and rejects a larger new mutation while preserving the record. Receipt count stays 512; target ID length is 192. The schema now also bounds stored signature/target lengths. Previously hand-crafted envelopes outside those new limits become recovery-required; no production envelope activation has occurred in these reviewed stages and raw recovery export remains available.

## Outstanding integration gates

The original six lifecycle replay failures are not rerun or closed by this primitive suite. Subscribers must use canonical semantic operations, await durable commit, publish the domain-change notification only after success, and correlate the current attempt. The existing synchronous event-bus `perform` plus WeakMap early-success path cannot remain authoritative. See [prepared integration constraints](20260909-c-primitive-test-preparation.md).

D must coordinate ordinary writes/reset/import/rollback and generation publication. Parent's fixed migration write-race evidence remains a concrete blocker; a per-dataset C lock alone does not prevent migration from publishing an earlier copied snapshot. The preferred account lifecycle shared/exclusive lock protocol and noncanonical-writer scope are documented in the preparation review.

No production activation is authorized. The [runtime activation gate](20260909-runtime-activation-gate-diagnosis.md) remains unimplemented/unverified for universal old-client drain. Parent's separate native multi-document/reload probe was still in progress when this report was written and is not counted here. Its future result can add a browser evidence layer without converting this bounded primitive verdict into full AI-02 or release acceptance.
