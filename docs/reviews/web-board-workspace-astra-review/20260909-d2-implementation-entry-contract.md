# D2 implementation entry — account lifecycle and all participating writers

Astra architecture handoff, Web, 2026-09-09. Extends approved `9df552e` and `7b95133`; inputs: parent inventory `4e9ff08` (`20260909-d2-writer-inventory.md`) and migration/autosave failures, most recently fixed `0b236cd` rerun in `54b422c` (3 FAIL / 2 controls). This is an implementation contract, not product code, acceptance or a new rollout authorization.

**The author can begin D2 with this contract.** Start by binding the inventory to an explicit caller/ownership checklist and implementing the shared coordination API. There is no need to change the two physical canonical keys, add a journal key for receipts, or replace the backend. Do not claim all-account completion until every supported current-client writer below participates and its callers await truthful results. Coordinate Tasks ownership with Sol before changing its call sites.

## Required API and lock semantics

1. Centralize one account lifecycle lock name derived from account/demo identity and account ID, **excluding generation**. Both old and new generations must contend on the same account lock. Ordinary writers acquire it in shared mode, then acquire any existing dataset/timer/domain exclusive lock. Migration, rollback, import publication and account deletion acquire it exclusively before reading the source snapshot and hold it through verification and visibility commit. Never acquire account coordination while already holding a domain lock. Existing migration-only and dataset-only locks are not substitutes.
2. Add explicit Promise-returning account writer entry points (e.g. async typed-pref set/remove, autosave set/remove, scoped-storage wrapper), rather than making existing boolean/void methods secretly return Promises. Return an explicit committed/refused result; a caller may not close an editor, clear a pending draft, advance deletion phase or acknowledge success until the operation resolves. Read-only `getPref`/projection surfaces can remain synchronous. Device-only keys stay under their classified device contract.
3. Capture owner before enqueueing; after account-lock and domain-lock waits, recheck captured owner, persistent generation marker and tombstone before mutation and before publication. Use the same C/D1 receipt-preserving dataset engine inside the account lock. Generation changes while waiting refuse the old operation; do not retarget its draft into the newly active account/generation. Lock unavailability/rejection is a typed failure with no unfenced fallback write.
4. Guard old synchronous account mutation APIs when coordinated mode is admitted: explicitly refuse rather than bypass the account lock. Convert all current production callers before that admission. A temporarily retained legacy/default-off path must be labeled uncoordinated and cannot count as D2 completion. Async hook/callback consumers must await results; a Promise's truthiness is never success. Exported `createScopedStorage` also needs an async guarded surface or explicit refusal of its old account setters, even if no current internal consumer was found.
5. Migration should also compare the complete copied source key set and raw bytes before publication, detecting additions/removals as well as changed values; preserve raw envelope/receipt bytes. This is defense against incomplete participation and keeps the original stage/verify refusal-or-preservation oracle useful. It does not replace shared/exclusive locking or prove safety against arbitrary old JavaScript racing after the final comparison. Keep the legacy failures/control assertions; add separate current-async-writer cases rather than weakening them to assert merely that some error occurred.

Use an internal already-held-lock context for lifecycle raw copy and secret stage/verify operations. They must not recursively request a shared lock beneath an exclusive lock. For an operation genuinely spanning two accounts, acquire account locks in one stable sorted order; the ordinary one-account paths must not acquire arbitrary nested account locks.

## Writer and lifecycle ownership to implement

| Owner surface | Required participation |
| --- | --- |
| `plugin-web-storage`: storage APIs, hooks, `canonicalCommandState`, `accountScope` scoped wrapper | Central account lock/admission, explicit async result APIs, preserved C/D1 semantics, guarded synchronous account bypasses, all indirect typed/autosave callers tracked |
| `accountMigration.ts` | Same account-exclusive lock for snapshot → stage/verify → marker publication and rollback; source revalidation; raw records/receipts retained; no fallible success-critical post-commit bookkeeping |
| `accountDataLifecycle.ts` and Settings `accountDeletionRecovery.ts` | Async exclusive tombstone/local deletion; recovery caller awaits completion before phase advancement; partial failures remain tombstoned/retryable, never report cleanup complete early |
| Bookkeeping and Metrics storage wrappers | Convert direct physical account writes and caller result handling; preserve failed drafts and existing validation |
| Time Tracker storage and `TimeTrackerModule.writeTrackerUi` | Coordinate both account-owned paths; classify its device mode preference separately; acquire account before existing timer/data lock |
| Pomodoro and Meditation controllers | Account lock must enclose the existing ordered active/history/settlement work; preserve timing, issued intent, retry and no-duplicate settlement contracts |
| AI provider `secretStore` | Ordinary provider-secret updates must participate too, not only migration's stage/verify participant; same account coordination before secret/domain lock and through awaited persistent completion |
| Board, Tasks list/tag metadata, conversation/settings and all other indirect account-pref/autosave consumers | Convert writer callers or explicitly withhold coordinated activation until converted; a shared helper change alone is not evidence every caller understands async failure |

The checklist must record logical key/store, account versus device classification, physical writer/helper, callback owners, lock ordering, success/refusal semantics and fixed test evidence. Also search computed storage calls and stores beyond localStorage; the parent raw-write inventory is a concrete starting list, not proof of exhaustiveness.

Secret/auth cleanup is not a multi-store transaction merely because account data is locked. Keep ordinary secret writes fenced against migration/deletion; stage ciphertext before the sole generation visibility commit, and retain retryable deletion phase state for subsequent secret/auth/network failures. Do not hold unrelated provider network requests under the account lock. A multi-store operation that cannot use this ordering must be explicitly designed before that slice is implemented, not silently excluded from an all-account claim. Coherent full-account export needs a protected snapshot (short exclusive snapshot interval or a verified equivalent); byte-preserving export is not permission for uncoordinated import.

## Independent acceptance and remaining gates

- Retain the original default-off migration stage/verify and autosave FAIL/control tests. Add real async current-client writers before/during migration, rollback and deletion, including command receipt replay, ordinary UI edits, autosave, a direct business writer, timers and ordinary secrets. Inspect the final visible generation and reported result: no acknowledged update may be stranded only in the previous generation.
- A writer submitted after the lifecycle exclusive lock is held waits, then refuses its stale captured generation after publication; it must not claim to have committed. Writers already committed before the exclusive lock is acquired must be represented in the copied generation. Timers and multi-record settlement need their existing correctness tests plus these lifecycle interleavings.
- Schedule competing writers independently. Never await a shared-lock writer inside migration's exclusive-held stage/verify callback; that would deadlock the test by construction. Use barriers to start the competitor, release the lifecycle work, then await both outcomes. Add lock-order, failure/retry, same-account two-controller and native two-document checks.
- Preserve deletion recovery/export safety and verify that old callbacks cannot recreate tombstoned data. Fault actual persistence/secret operations; do not turn injected refusal into fake local success.

Current-client coordination and the initial old-client rollout are different gates. `20260909-runtime-activation-gate-diagnosis.md` still applies: new Web Locks cannot stop old direct `localStorage.setItem`, stale caches and resumed old processes are not universally drained, and the present runtime lacks a proven universal admission mechanism. Keep production activation closed except for explicitly proven controlled populations. Public universal old-client safety needs a separate operator-level rollout/authority decision; it must not block writing/testing the compatible-client D2 implementation or be falsely claimed solved by it.

Even a completed D2 implementation would not by itself close full AI-02/REL-05, Tasks' current UI failures, Board detail drafts, all native interaction combinations, provider-network evidence, or release readiness. This document authorizes no deployment and does not implement any lock or migrate data.
