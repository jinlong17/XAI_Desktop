## Independent outcomes

1. **Before ab8c35a^:** server success followed by native auth revoke abort leaves A active but the old v1 receipt already complete. Reload enumerates zero pending receipts. `before.log` PASS means the old defect was reproduced, not acceptance.
2. **After ab8c35a:** the same server-success / auth-abort sequence retains a version2 `local-data-cleared` receipt with the exact original authGeneration and separate business generation. A's durable auth pointer remains active, so this is not a simulated already-cleared success. Reload exposes the actual recovery button.
3. **Replacement:** actual SDK password sign-in publishes B. Clicking the actual RecoveryNotice button retries captured A through the host bridge. A is revoked, the receipt completes, B's active generation, actual persisted SDK session bytes and business bytes remain identical. No second account-delete HTTP request occurs. B login already revokes its predecessor as part of normal coordinator behavior; this case therefore proves idempotent A retry / B preservation, not a claim that A's first revocation occurs during retry.
4. **Final-marker quota:** deleting B succeeds server-side, native auth is revoked, but writing receipt complete fails. The receipt remains discoverable. Reload then actual Retry finishes, auth stays absent, and server-delete count remains two across the two distinct A/B deletions.
5. **Version boundaries:** v1 local receipt completes without invoking or inventing an auth generation. A v2 receipt without an auth participant remains pending and throws. Receipt metadata contains account/generation/phase/time only, no session tokens.
6. Actual styled notice at 390px visually inspected: wrapping and retry button fit; screenshot `390px-auth-failure-after.png`. The top unstyled status/delete controls are explicitly harness UI.

After evidence: `after.log`. Faults are exercised with correct postconditions independent of author test assertions. ## Boundaries still open

This verifies the auth-generation participant's durable receipt and retry integration only. It does not prove all account data has been erased. AI secret cleanup uses its real implementation but no populated secret corpus is seeded here; encrypted-cache/device/legacy auth participants and blocked-database upgrade recovery are not claimed. It does not close unknown server outcomes, first durable intent/receipt failure, cross-tab deletion concurrency, account recreation, full-host routing/navigation, production services or general REL06 acceptance. Old v1 receipts cannot safely recover an unknown historical auth generation; support deliberately remains their original participant scope.
