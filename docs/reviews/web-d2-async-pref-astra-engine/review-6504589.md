## Source review and repaired behavior

`prefMutation.ts` now composes caller validation with a shared strict runtime codec validator and registered domain validation. Exceptions from the validator become false validation rather than escaping the Promise result. Registered key/codec mismatches refuse before mutation. The selected permission enum is consistently enforced through the engine and public adapters. The dynamic-absence exception requires reset, an unregistered binding and an actual undefined absent representation; it cannot suppress registered default validation. `storage.ts` resolves the registered default for autosave removal, so the actual subscriber receives `comment` rather than undefined. Legitimate registered string/boolean, dynamic JSON empty array and dynamic reset controls still pass.

All four public Account set/remove/autosave APIs retain the same account-shared → full-physical-key-exclusive ordering. The original controls continue to cover latest persisted functional input, raw baseline conflict, failed reads, canonical refusal, queued owner/marker/tombstone changes, device-only key locking, observer exception isolation, and before/during migration interaction. The engine changes do not modify lifecycle coordination or production activation.

The token interface solves the previously impossible original-baseline retry after a physically successful write whose readback failed: the failure now carries `retryToken`; the caller can present it as `reconcileToken` while retaining the original `expectedRaw`. The process-local entry binds full physical key, original raw, intended raw and set/reset kind. The physical key includes account/demo identity and generation. Account admission is checked again inside coordination before any lookup can grant reconciliation.

On a baseline mismatch, token reconciliation additionally requires current bytes to equal the original operation's intended state; it never authorizes a new set/remove to a different target value. Successful reconciliation consumes the token before notifying, publishes the verified outcome once, and returns `changed: false` without another physical mutation. The new tests observe actual set/remove call counts and notification values for both set and reset. They also establish:

- Wrong token, changed original baseline, different key with matching intended bytes, changed intended value, and wrong operation kind all refuse the stale-baseline attempt; a still-valid original token is not consumed by these unrelated attempts.
- A current different account or generation cannot reuse the token, and incomplete persistent markers/tombstones still refuse before notification.
- An observed external replacement invalidates the token. Even if intended bytes are later put back, the stale original-baseline token cannot be revived.
- Successful token reuse is refused on the second original-baseline replay. Pre-write quota failure issues no token and cannot justify skipping a later conflict.
- Public Account wrappers retain their original no-token same-intended retry reconciliation for both set and removal. This also consumes the corresponding engine token, so it cannot later grant a second stale-baseline reconciliation.

The token is an internal attribution mechanism, not a durable receipt or a new storage key. It is not authorization to adopt a different owner's draft. Hooks remain responsible for capturing their original immutable operation, forwarding the token only for that operation, and suppressing obsolete session completions; this review does not inspect Sol's pending hook changes.
