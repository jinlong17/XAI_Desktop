### GOV-01: package dev_log inputs

Source enumeration in scripts/dashboard/generate-state.mjs is limited to immediate directories under packages, then the exact packages/<directory>/docs/dev_log.md path. It does not enumerate status blocks within the file. parseStatusPanel parses Markdown tables, chooses the first table whose headers include Field and Value, or otherwise the first Markdown table, and maps rows into a single key/value object. scanDevLogs emits one item per package with package, feature, classified status, raw status, updated, suggested next/workflow, and path. It drops items with an empty raw Status. It emits aggregate item counts, source_count and shipped; it does not emit discovered, unparsed, per-file coverage, stable Target IDs, or iteration identity. Code anchors: scripts/dashboard/generate-state.mjs:1452-1486 (table parsing), :2137-2149 (status panel selection), :2153-2196 (classification and scan); docs/prototypes/dev-dashboard/js/tasks.js:1-24 (Task Progress rendering).

The shared table reader splits rows on every pipe and retains rows only when cell count is at least the header count. Rows with too few cells disappear; excess cells are not represented in the output. Exceptions in the roadmap reader become null or an empty manifest list, while the dev_log scan has no per-file error record. classifyDevStatus maps non-empty unknown strings to OTHER, but the later empty-status filter prevents an empty record from reaching that state. The task page renders one row per output item, links to the source file, and does not expose unparsed sources or iteration selection.

The original audit cites four concrete format examples: Time Tracker has plain Status and workflow metadata, including multiple dated status sections; Bookkeeping has a Field/Value table with Target and Status; Metric Tracker uses a Status heading and work-log content; Plugin Project has a bullet-form Status Panel with Target and Updated (docs/reviews/20260908-full-product-audit/01-inventory-governance.md:25-32, 304-316). The source records require all formats and multi-iteration fixtures to be covered. These examples establish why one-table parsing is an incomplete candidate; they do not prove how many current files would be omitted. Existing text fields are not equivalent to a stable Target/iteration key. In particular, package identity alone cannot preserve multiple independent workflow rows.

Finite root-cause hypothesis: the discovery boundary is broader than the parser contract. The parser recognizes one table shape and one status per package, then filters missing status without retaining a rejection record. The 2026-09-08 audit's named examples align with those static limitations. A source-only read cannot establish the present discovered/parsed/unparsed counts or prove every historical omission remains.

Candidate future correction: enumerate the same package/file boundary, parse each recognized status block with its source line range, and account for each discovered file and each candidate block as parsed or explicitly unparsed with a reason and raw-source identity. Preserve the original text/status and unknown formats; do not discard them or coerce them to a business state. Use Target plus explicit iteration metadata where present. Where a source has no stable identity or there are multiple competing current-status blocks, retain all candidates and report ambiguity until the contract defines selection; do not infer that the last block is authoritative solely from position. Any display aggregation must retain the full row set and make its selection rule explicit.

Future oracle and focused test scope: a fixed fixture matrix covering Field/Value tables, bullet panels, plain-text fields, Status headings, malformed table rows, empty/unknown statuses, escaped or embedded pipes, duplicate Target rows, and multiple iterations. Assert source-file conservation: every discovered file and status candidate is represented as parsed or unparsed with exact file/line identity; parsed plus unparsed partitions the discovered set without silent loss. Assert stable Target/iteration linkage and that unknown or malformed rows do not disappear or become an inferred SHIPPED state. This is a proposed oracle, not a test run or an approved test contract.

### GOV-02: roadmap manifest inputs

listRoadmapManifests enumerates every top-level .md file under docs/workflow/roadmap and calls parseRoadmapManifest. That parser recognizes only a table having #, Slug and Status headers. It keeps number, slug, normalized status and Last Run, then filters out rows lacking slug or status. It currently discards Source and Depends On fields even when the table contains them. Thus the reader can find files yet suppress a manifest because the required header signature is stricter than the documented rows. The three historical AI source manifests at this checkout each have Slug, Source, Depends On and Status headers without #; static source comparison predicts they do not satisfy the present signature if evaluated, but this discovery did not invoke that parser. Code anchors: scripts/dashboard/generate-state.mjs:1531-1558 (manifest parser), :1560-1575 (file discovery), :1640-1661 (explicit product tracking projection).

There is a second integration boundary: dashboard-state.json web.tracking.roadmap_manifests is an explicit filename list and does not include these three AI manifests. buildProductLines uses that list to select manifests for the Web module. Making the parser accept optional # alone may expose rows to the global roadmap signal but will not necessarily attach those manifests to the Web module. That registry relationship requires a separately reviewed, exact-scope decision.

The source rows are Slug xai-web-ai-tool-layer, xai-web-ai-tool-edit-delete, and xai-web-ai-tool-openai-compatible. Each currently records NEEDS_REVIEW in its manifest, and each has a corresponding Target section in packages/xai-web-ai-chat/docs/dev_log.md with SHIPPED text. This is a source-record conflict worth surfacing. It is not authority to rewrite either source, infer runtime acceptance, or substitute the dev_log status for the authored roadmap status. GOV-02's 167 is the historical expected set; no current parsed total was measured here.

Finite root-cause hypothesis: an otherwise valid manifest table is rejected when it omits the optional row-number column. In addition, the hand-maintained Web manifest allowlist omits the three files, and the output row schema does not preserve Source/Depends On for structural review. These are two distinct boundaries; only changing the header predicate would not close the module-linkage or schema-visibility portions of acceptance.

Candidate future correction: recognize a manifest from required semantic columns Slug and Status, treating # as optional; preserve an absent number distinctly from a supplied value; capture Source and Depends On; report duplicate/missing required fields and malformed rows as explicit unparsed records. Reconcile the discovered manifest set against the configured module association, with an explicit unassigned/ambiguous outcome instead of silently treating a discovered source as a Web row. Preserve source status as authored and surface disagreement with Target/iteration evidence without automatically choosing a winner.

Future oracle and focused test scope: fixtures for tables with and without #, required columns in varying order, valid and empty rows, missing Slug/Status/Source/Depends On, duplicate slug, malformed row width, non-manifest Markdown, duplicate targets, and all three AI manifests linked to their exact Target sections. Assert every discovered roadmap file is either an accepted manifest or an explicit unparsed non-manifest/error record; assert parsed plus unparsed coverage equals discovered. Assert Slug/Status/Source/Depends On are visible, optional number is retained when present and absent when missing, and module association is explicit. Check the historical expected total only against a pinned complete source inventory and explain any delta; do not hard-code 167 as a length guard or treat unknown counts as zero.
