# Roadmap Seed — x25519-device-keypair

> sync-v1 roadmap · feature #12 · wave W1 · Phase 0.3
> Source PRD: docs/planning/sub-prds/sync/PRD.md v0.6-DRAFT · dev-plan task(s): T-06/T-08 (device key generation)
> Status hint: PENDING

## Requirement
Generate the per-device X25519 keypair using **local CSPRNG** (`device_priv = csprng(32)`), compute `device_pub`, store `device_priv` only in macOS Keychain (`xai.devicekey.<account_id>.<device_id>`, WhenUnlockedThisDeviceOnly, ACL=bundle id), zeroize the in-memory copy, and upload `device_pub` to `sync_devices.device_pub`.

## Hard constraints
- PRD §3.1 invariant #3 / FR-SY-76 (C-A): device_priv MUST be generated by local CSPRNG independently — ⛔ NEVER derived from KEK ⛔ (else old devices compute new-device device_priv and per-device wrap collapses). Fixed v0.4 C-A / R-10.19.
- Validate received `device_pub` (reject all-zero / low-order points, RFC 7748) — stride-cve §3 #3 footgun.
- device_priv resident in Rust KeyVault when needed (FR-SY-75); only the Keychain copy persists.
- Code boundary: `apps/desktop/src-tauri/src/crypto/` + Keychain via `platform/macos/` per codebase-orientation §5/§6.

## Threat model binding
- T11 (revoked device decrypts new data): CSPRNG-independent device key means old devices cannot compute a new device's private key (PRD §2 T11, FR-SY-76, R-10.19).
- STRIDE Elevation-of-Privilege across TB-2/TB-4 (KeyVault / Keychain).

## Acceptance signal
device_priv generated via CSPRNG (provably not KEK-derived), stored in Keychain only, in-memory copy zeroized; device_pub uploaded; low-order/all-zero pub rejected.
