## 3. Proposed business and source contract

These clauses require fresh independent contract review. They are a complete proposal, not self-approval or a source-edit permission.

1. **Absence versus deliberate empty.** Source `absent` with no draft displays the existing four cities in order: shanghai/london/new_york/tokyo, without writes. Source `valid` with JSON `[]` displays zero cities, localized empty state and a reachable Add city entry in each view, after same-mount updates, route reopen, reload and whole-browser reopen. Last-city removal writes exactly JSON `[]` as a **set**, never a key deletion/reset. Add from empty writes `[id]`; remove then re-add preserves user order by appending. Duplicate add is inert.
2. **Field domain.** Proposed strict caller domain: ordered unique array of the 12 exact ids, length 0–12. All ids derive from frozen CITY_LIBRARY, no copy of offset data. JSON `null`, primitives, objects, non-string items, unknown/mixed ids, duplicates, case/whitespace variants and malformed JSON are source-invalid. Do not silently filter, deduplicate, repair, normalize or overwrite stored malformed data. This deliberately replaces the legacy unknown-filter test; the bytes remain intact and recoverable through the existing account-data surface, which this caller does not implement. Domain tightening requires a pre-before cross-caller seed scan and independent review; no registry/migration schema tightening is authorized.
3. **Source truth.** Absent and valid-empty are healthy. Invalid/unreadable source safely displays the existing fallback cities plus a source-only alert and field-local Reload; there is no new unsaved draft, inline export, departure hold, unload warning or success claim. A choice over this source is actual failed work, displayed as a draft and preserved; the engine must refuse the write. External source repair does not acknowledge that draft. Reload checks live actual-work identity and refuses to erase it; explicit Discard detaches work first and then safely rereads the current field. Read failures are scoped to the captured physical city key or a specifically named lifecycle control, never all App keys at load.
4. **Editing.** Keep one coherent account-bound city-list draft and exact operation identity. Add/delete applies to latest displayed list, including preceding pending edits; submit an absolute array via registered async edit to retain expected raw baseline and uncertainty grant semantics. Do not read current storage in a functional updater to merge unseen external edits. A new action may be a new operation; Retry must retain its held failed operation/token, not synthesize a new edit. Do not infer latest success from array equality, hook status, predecessor promise or persisted value alone.
5. **Views and style.** List/analog/grid switch immediately and remain current across edits, failures, picker actions, ticks and same-mount reorders/resizes. Reopen defaults to list, as today. Switching views changes no city bytes, draft identity, guard, export or persistence operation; pending recovery remains accessible. Widget appearance controls belong to grid and do not become WorldClocks persisted fields. No new view preference or reset feature is invented.
6. **Empty and full states.** Empty text: `No cities added.` / `尚未添加城市。`; empty CTA `Add city` / `添加城市`, same picker as the header. Twelve selected cities show existing `all_added` state; no duplicate or invisible action. Empty list is an actual usable state in all views. Header/empty entry and picker controls preserve no-drag behavior. No automatic default seed on view change, tick, removal, ghost render, mount or reopen.
7. **Date and offset acceptance.** Today/Tomorrow/Yesterday compare the city's calendar date at the same instant against the user's current local calendar date, not against UTC or a previously mounted date. All three views must agree on city/time/day label/offset. Preserve list AM/PM, grid night thresholds (before 06:00 or from 19:00), analog hand semantics and 12-city fixed-offset model.
